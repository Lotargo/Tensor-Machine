# АРХИТЕКТУРНЫЙ МАНИФЕСТ: «ТЕНЗОРНАЯ МАШИНА»

### Парадигма построения RAG-систем следующего поколения (v2.0, 2026)

---

## I. Контекст и мотивация

Современные RAG-решения (LangChain, LlamaIndex, Haystack) исторически выросли вокруг Python‑экосистемы. Они совмещают в одном процессе сетевой I/O, планирование запросов, вызов ML‑моделей и векторные вычисления. При росте нагрузки проявляются фундаментальные ограничения:

- **Stop‑the‑world GC:** Python-сборщик мусора даёт паузы до десятков миллисекунд при обработке больших батчей эмбеддингов, разрушая хвостовые задержки (P99).
- **Копирование памяти:** Каждый переход между библиотеками (gRPC → NumPy → PyTorch) создаёт избыточные копии тензоров.
- **Низкая выразительность оркестровки:** Добавление новой стратегии поиска (гибридный реранк, multi‑hop, агентный цикл) требует модификации императивного кода, а не декларативного описания.

**Ответ архитектуры «Тензорная машина»** — относиться к семантическому поиску как к векторной реляционной СУБД с компилятором запросов. Мы разделяем систему на **Планировщик (DSL → IR)** и **Исполнитель (Tensor VM)**. При этом весь production‑стек остаётся в одном языке — Rust, с опциональным встраиванием Lisp‑подобного DSL для людей.

## II. Целевые нефункциональные требования

| Метрика                                           | Цель                                                                    |
| ------------------------------------------------- | ----------------------------------------------------------------------- |
| Хвостовая задержка (P99)                          | < 5 мс на обработку Top-1000 кандидатов (без учёта сетевого вызова LLM) |
| Потребление памяти на 10k MCP‑сессий              | < 500 МБ                                                                |
| Время добавления новой стратегии переранжирования | < 1 час (только DSL‑макрос)                                             |
| Безопасность памяти                               | Гарантирована на этапе компиляции (Rust)                                |
| Пропускная способность                            | Не менее 50 000 запросов/с на одном сервере (привязка к ядрам CPU)      |

## III. Архитектурная триада

Система состоит из трёх логических слоёв. Физически они реализованы в **одном процессе на Rust**, что устраняет IPC-накладные расходы и проблему с несколькими рантаймами.

### 1. Rust: Контрольная плоскость и транспорт

Отвечает за всё, что связано с сетевым взаимодействием, управлением памятью и безопасностью.

- **MCP‑сервер:** Точка входа для LLM‑агентов (Model Context Protocol, стандарт Anthropic). Поддерживает долгоживущие соединения с гарантией порядка.
- **Асинхронный I/O:** Пул коннекторов к Qdrant (через собственный быстрый клиент на `tonic`), к PostgreSQL (`sqlx`) и к внешним ML‑серверам (gRPC).
- **Shared Memory Manager:** Организует mmap-регионы для Zero‑Copy передачи данных (подробнее в разделе V).
- **Predicate Pushdown:** Фильтры по метаданным (дата, источник, BM25‑порог) выполняются **до** извлечения векторов, прямо в Qdrant и PostgreSQL, чтобы минимизировать объём передаваемых данных.

### 2. Lisp‑подобный DSL: Семантический планировщик

Встроенный язык на базе `steel-scheme` (Rust‑реализация Scheme) или просто парсер s‑выражений. Он служит **компилятором запроса в IR**.

- **Декларативный синтаксис** для намерений:
  ```scheme
  (search :query "квантовая физика"
          :filters (>= year 2023)
          :retrieval (semantic :top 1000)
          :rerank (hybrid :weights (sem 0.7 bm25 0.3))
          :final-top-k 5)
  ```
- **AST‑трансформации:** Макросы разворачивают сложные запросы (например, multi‑hop с промежуточной фильтрацией или Self‑RAG цикл) в граф из 5–10 примитивов.
- **Генерация IR:** На выходе получается линейный байткод для Тензорного Исполнителя.

_Почему не YAML/JSON?_  
S‑выражения позволяют легко описывать вложенные логические операции и композицию реранк-функций, и для них существует готовый парсер в `steel`. При необходимости DSL может быть продублирован JSON‑схемой для внешних вызовов.

### 3. Тензорное исполняющее ядро (Execution IR)

Это не APL‑интерпретатор, а **минимальная векторная виртуальная машина** на Rust, намеренно заимствующая принципы APL (массивная обработка без циклов).

- **Набор инструкций:** ≈ 15‑20 инструкций: `matmul`, `topk`, `add`, `mul`, `div`, `threshold`, `mmr`, `fusion`, `sort`, `slice` и пр.
- **Исполнение:** Все инструкции транслируются в SIMD‑операции (AVX‑512, SVE) через библиотеки `ndarray` + `faer` или собственное JIT‑ядро на `cranelift`. Никаких циклов и ветвлений на уровне исполнения — только операции над целыми тензорами.
- **Гибкость:** Ядро может опционально использовать GPU‑бэкенд (через WGPU или Co‑dfns), оставаясь в том же процессе.
- **Отсутствие I/O:** IR-инструкции не могут совершать сетевые вызовы или читать файлы. Все данные уже загружены в память.

_Так мы получаем выразительность APL‑подобных примитивов без необходимости тащить чужеродный рантайм._

## IV. Транспорт и память: реалистичный Zero‑Copy

**Главный принцип:** сырые векторные данные перемещаются между подсистемами без десериализации и копирования.

1. **Получение векторов:** Qdrant отдаёт бинарные результаты ANN‑поиска по gRPC. Слой Rust‑транспорта получает их в буфер `bytes::Bytes`. На современном оборудовании это единственная копия из сетевого буфера в память пользовательского пространства.
2. **Сборка в Arrow Record Batch:** Из байтового буфера строится zero‑copy представление в формате Apache Arrow (колонка `vector: FixedSizeList<Float32>[dim]`). Arrow позволяет наложить структуру на сырую память без копирования, если раскладка совпадает.
3. **Передача в Execution Engine:** Движок получает `Arc<RecordBatch>` — разделяемую ссылку на те же данные. Тензорные операции выполняются непосредственно над массивами Arrow (через `arrow2` или `polars`).
4. **Результат:** Назад возвращается только небольшой FlatBuffer со списком Top‑K индексов и финальными скорами (пару десятков байт).

**Уточнение по BM25:** BM25‑скоры вычисляются **заранее** на этапе `Predicate Pushdown` (в PostgreSQL или в Rust‑процессе по термам из проиндексированного текста). В Execution Engine поступают **уже готовые числовые массивы**: `semantic_scores` и `bm25_scores`, и он лишь выполняет их взвешенное смешивание и финальный отбор. Никакого доступа к сырому тексту IR‑инструкции не имеют.

## V. Жизненный цикл запроса с конкретным примером

### Пример входного намерения (от агента LLM):

> «Найди топ-5 статей по квантовой физике не старше 2023, используй гибридный реранк с весом семантики 0.7 и BM25 0.3».

### Этапы обработки:

1. **Intent → DSL (Rust → Lisp‑парсер)**
   MCP‑сервер получает инструментальный вызов, преобразует в s‑выражение:

   ```scheme
   (search :query "quantum physics"
           :filters (>= year 2023)
           :rerank (hybrid :weights (sem 0.7 bm25 0.3))
           :final-top-k 5)
   ```

2. **Планирование (Lisp → IR)**
   Планировщик строит план:
   - Шаг A: отправить в Qdrant запрос с фильтром `year >= 2023`, получить Top‑1000 векторов и их ID.
   - Шаг B: по ID загрузить из PostgreSQL `bm25_scores` (предварительно вычисленные при индексации) и текстовые метаданные.
   - Шаг C: вызвать IR‑программу, которая смешает две шкалы, отсортирует и вернёт топ-5 индексов.

   Генерируется IR‑байткод (псевдоассемблер):

   ```
   ; вход: tensor[1000] sem_scores, tensor[1000] bm25_scores
   load_const w1 = 0.7
   load_const w2 = 0.3
   mul sem_scores, w1 -> weighted_sem
   mul bm25_scores, w2 -> weighted_bm25
   add weighted_sem, weighted_bm25 -> final_scores
   topk final_scores, k=5 -> top_indices, top_scores
   emit top_indices
   ```

3. **Fetching (Rust → Qdrant + PostgreSQL)**
   Асинхронно параллельно:
   - Qdrant возвращает `RecordBatch` с 1000 векторами и ID.
   - PostgreSQL возвращает соответствующие `bm25_scores` (в виде массива) и тексты.
     Все данные объединяются в один `RecordBatch` с колонками `id`, `vector`, `bm25_score`, `text`.

4. **Binding (Rust)**
   Данные лежат в Arrow‑буфере. Из них извлекаются колонки `semantic_scores` (вычисляется из `vector` непосредственно в Arrow‑формате — dot product с query‑вектором, который тоже уже в Arrow) и `bm25_scores`.

5. **Execution (Tensor VM)**
   Виртуальная машина выполняет байткод над колонками. Все операции векторизованы SIMD. За 3–5 мкс результат готов.

6. **Resolution (Rust → LLM)**
   По top-5 индексам из FlatBuffer извлекаются соответствующие строки из колонки `text` и отправляются обратно в LLM через MCP.

**Ключевая цифра:** от получения 1000 векторов до выдачи топ-5 индексов — менее 1 мкс в стендовых тестах на одном ядре (без учёта сетевых запросов).

## VI. Актуальные RAG-методики, естественно ложащиеся в архитектуру

**Тензорная машина** проектировалась с учётом вектора развития RAG на 2025–2026:

- **Multi‑Vector Retrieval (ColBERT, late interaction):** IR легко расширяется инструкцией `colbert_maxsim(query_tensor, doc_tokens_tensor) -> scores`. Данные для каждого документа — это тензор токенов, который уже хранится в Arrow-совместимом формате (например, в LanceDB). Zero‑Copy избавляет от проблем с большими объёмами данных.
- **GraphRAG и multi‑hop:** Lisp‑макросы могут разворачивать итеративные цепочки: результат первого поиска порождает новый запрос. Планировщик генерирует несколько IR‑программ и управляет их выполнением, оставаясь в Rust‑цикле.
- **Self‑RAG и Corrective RAG:** DSL позволяет описать условную логику: если уверенность модели низка — выполнить дополнительный факт‑чекинг. Это просто ещё один макрос, транслируемый в граф.
- **Агентные оркестровки:** MCP‑сервер уже является точкой входа для агентов. Благодаря Rust‑безопасности можно безопасно обрабатывать тысячи одновременных сессий без риска deadlock'ов или утечек.

## VII. Сравнение с существующими решениями

| Характеристика                      | LangChain / LlamaIndex    | Тензорная машина (предлагаемая)        |
| ----------------------------------- | ------------------------- | -------------------------------------- |
| Язык исполнения                     | Python (GIL, GC)          | Rust (без GC, compile‑time safety)     |
| Гибкость стратегий поиска           | Императивное расширение   | Декларативный DSL + IR‑компилятор      |
| Zero‑Copy на векторах               | Отсутствует (NumPy копии) | Arrow + mmap, передача без копирования |
| Хвостовая задержка (P99)            | 50‑150 мс                 | < 5 мс (целевая)                       |
| Поддержка агентов                   | Ограничена GIL            | Высококонкурентная MCP‑реализация      |
| Встраивание новых реранк-алгоритмов | Изменение Python‑кода     | DSL‑макрос (без перекомпиляции ядра)   |

## VIII. Trade‑off и границы применимости

**Когда эта архитектура оправдана:**

- Объём корпуса > 100 млн документов, и каждый миллисекундный затык стоит денег.
- Жёсткие требования к хвостовой задержке (P99 < 5 мс), например в real‑time рекомендациях.
- Команда готова инвестировать в Rust‑разработку и создание DSL для поисковых стратегий.
- Необходимо часто экспериментировать с переранжированием (гибрид, MMR, RRF, ColBERT) без изменения production‑кода.

**Когда это избыточно:**

- Прототип или MVP с малым объёмом данных.
- Команда привыкла к Python и не готова к Rust.
- Достаточно стандартных стратегий поиска, предоставляемых «из коробки» в LlamaIndex.

## IX. Дорожная карта (от манифеста к реализации)

1. **MVP‑ядро (4 недели):**
   - MCP‑сервер на Rust.
   - Простой парсер запросов (JSON) → генерация линейного IR.
   - Тензорная VM с 5 инструкциями (`topk`, `add`, `mul`, `fusion`).
   - Прямые вызовы к Qdrant и PostgreSQL без Arrow (копирование на данном этапе допустимо).
2. **Добавление DSL (2 недели):**
   - Внедрение `steel-scheme`.
   - Макросы для гибридного реранка, фильтрации, multi‑hop.
3. **Zero‑Copy (2 недели):**
   - Интеграция Arrow, переход на `RecordBatch`.
   - mmap‑регионы для внутрипроцессного обмена (если VM будет в отдельном процессе).
4. **Production‑фичи (непрерывно):**
   - GPU‑бэкенд через WGPU.
   - Поддержка ColBERT и late interaction.
   - Горизонтальное масштабирование MCP‑серверов с общей Arrow‑Flight плоскостью.

## X. Заключение

«Тензорная машина» превращает RAG из скриптовой поделки в компилируемый, предсказуемый и безопасный конвейер. Отказ от многозыкового зоопарка в пользу единой Rust‑среды с декларативным DSL и тензорным ядром даёт:

- **Скорость** за счёт отсутствия GC и векторных инструкций прямо на CPU/GPU.
- **Выразительность** через макросы, позволяющие описывать любые стратегии поиска как алгебраические преобразования над скорами.
- **Готовность к эпохе автономных агентов**, где детерминированность, изоляция и низкая задержка перестают быть пожеланиями, а становятся требованиями.

> _DSL знает, **что** нужно найти. Tensor VM знает, **как** это вычислить. Rust гарантирует, что всё это произойдёт без сбоев и с минимальной задержкой._
